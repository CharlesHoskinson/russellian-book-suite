# Retrospective: v3 → v4.3 of the Bermuda Manual

Date: 2026-05-11
Scope: the work between the v3 regeneration (v2.0.0 release) and the v4.3 prose-furniture cut (v3.0.0 release, currently shipped at 80 pages).

## What got shipped

Each release added a discrete layer. The book grew from 53 pages of correct-but-soulless Russell prose to an 80-page editorial artifact with figures, tables, scenes, footnotes, and a thematic Further Reading list.

| Cut | Pages | What landed |
|---|---:|---|
| v2.0.0 | 53 | Russell prose; 222 verified claims; React/Tailwind browser; PDF via Playwright |
| v3.0.0 fast-path | 72 | 12 figures (hand-SVG + matplotlib); markdown tables; opening + mid-chapter scenes per chapter; ~40 glossary sidebars; preface + glossary + sources back matter |
| v4.1 | 73 | Mermaid CLI diagrams (4); real OSM-derived parish map; publication-themed matplotlib charts |
| v4.2 | 76 | great_tables hero tables (4); CSS-themed markdown tables (9) |
| v4.3 | 80 | Polished glossary blockquotes; 40 footnotes; 14-item Further Reading bibliography |

## Defect inventory — what broke and what I patched

Twelve distinct defect classes surfaced during the run. The ones I patched more than once point to systemic gaps in our pipeline, not one-off mistakes.

| Defect | When first surfaced | Patches needed |
|---|---|---|
| Orphan `[clm-NNNN-NNNNNN]` tokens in prose | v3 strip pass | 3 (chapter strip → manuscript strip → bare `clm-NNNN-NNNNNN` outside brackets) |
| "Claim ledger: clm-..." citation noise in footnote text | v4.3 | 1 (post-build sweep) |
| Numeric-ID footnotes added by an earlier agent (`[^1]: clm-2026-... — statement`) | v4.3 | 1 (39 defs + 78 refs stripped after the fact) |
| Chapter ordering mismatch (agent prompts used old chapter→title map) | v4 fast-path | 1 manual rearrangement of ch-02 through ch-05 after agents finished |

## Root-cause patterns

Four patterns repeat across the defect inventory.

**Pattern A — "fix-in-source vs. fix-in-rendered" leak.** Several defects (clm tokens, citation noise, ordering mismatch) lived in the chapter drafts but were detected in the rendered PDF. We patched the rendered output, then forgot to update the source, and the next rebuild re-introduced the defect. The pipeline lacks a contract that says "the source must be clean; the renderer is a pure function." Every patch I wrote needed to act on BOTH the chapter draft AND the assembled manuscript, otherwise the next `build_book` invocation would undo it.

**Pattern B — middle-chapter quality dip.** Across multiple agent-dispatch rounds, chapters 4–8 returned slightly lower-quality output than chapters 1–3 and 9–10. I observed this in v3 R3 (persona reviews) and again in v4 fast-path (expansion). The pattern is consistent with subagent context saturation when many similar prompts run in parallel and the dispatching agent runs longer than the cache TTL. No safeguard was in place; we accepted the variance.

**Pattern C — no post-build artifact QA.** Defects in the rendered PDF (the visible artifact the user judges) were caught only when the user spotted them. The pipeline has chapter-level acceptance tests (russellian linters, persona reviews) but nothing scans the FINAL ARTIFACT — the assembled manuscript.md, the manuscript.html, the manuscript.pdf — for the classes of defect that span chapter boundaries or that only manifest after rendering.

**Pattern D — agent prompts accumulated drift.** The chapter-expansion prompts I dispatched used a chapter→title map that was stale by one slot (legacy ordering vs. current contracts). Agents detected the mismatch and several saved to corrected slots; others did not. The root cause was that my prompts hard-coded chapter titles that should have been READ FROM the contracts at dispatch time. Prompt construction by string concatenation, without reading the source of truth, produces this class of defect every time the source of truth shifts.

## What v5 should solve

Five concrete deliverables, derived directly from the four patterns above.

1. **`book-qa` skill** — post-build artifact linter that scans the rendered manuscript.md, manuscript.html, and (where feasible) manuscript.pdf for the defect classes in the inventory. Runs after `build_book` and before "ship." Hard-fails on critical defects; flags but allows on minor ones.

2. **Per-chapter QA swarm** — after `build_book`, dispatch one QA subagent per chapter against a fixed checklist. Each agent returns a per-chapter quality report. A summary roll-up surfaces middle-dip patterns quantitatively rather than anecdotally.

3. **Cross-chapter consistency checker** — single agent (or single script) that compares all 10 chapter drafts for: terminology drift (Hamilton vs. Hamilton Parish vs. City of Hamilton), fact contradictions (Town Hill 76 m vs. 79 m), repeated content, paragraph-length variance per chapter.

4. **Contract-driven prompt construction** — dispatch templates that read chapter titles, contract acceptance tests, and verified-claim slices FROM SOURCE at dispatch time rather than from hand-typed prompt strings. Removes Pattern D entirely.

5. **Build-time contract on the assembled manuscript** — before the renderer touches `manuscript.md`, run a markdown-level lint pass against a curated checklist:
   - no `[clm-` tokens anywhere
   - every `<section>` and `<div>` closing tag followed by a blank line
   - every figure markdown reference points to a file that exists
   - every footnote `[^name]` has exactly one definition and at least one reference
   - heading hierarchy is monotone (no h3 without a preceding h2)
   - no `# Chapter N:` heading appears inside an HTML block

## Out of scope for v5

- Full skill-stack overhaul (the `book-craft` skill remains pending from the 2026-05-10 design doc; v5 should compose with it, not replace it).
- Generative-style improvements beyond linting (epigraphs, pull quotes, drop caps).
- Multi-book support (the workspace layout assumes one book; v5 stays per-book).

## Open questions for the design pass

- Should `book-qa` be a sibling skill or a sub-skill of `book-compose`?
- How does the per-chapter QA swarm coordinate findings into a single roll-up without inheriting the same context-drift problem?
- Should we adopt an editorial workflow analogy (dev editor → copyeditor → proofreader → fact-checker passes), each as a different persona, or stay with the existing 5+1 persona shape?

These get answered in the design doc that follows this retrospective.
